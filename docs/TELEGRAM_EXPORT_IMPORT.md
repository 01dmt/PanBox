# Telegram 导出导入

`app.py import-telegram` 把 Telegram 桌面版导出的频道记录导入 PanBox，写入的
不是文本清单批次，而是完整的入库记录：频道名、频道用户名、消息 ID、消息链接、
发布时间、原文，以及由原文解析出的来源、作品和 TMDB 关联。

```bash
python3 app.py import-telegram /path/to/ChatExport_2026-10-21 --channel lsp115
python3 app.py import-telegram /path/to/ChatExport_2026-10-21 --channel lsp115 --dry-run
```

全量导入（大批量）推荐这样跑，导入和匹配拆成两步：

```bash
# 1) 先只做来源校验和入库，不打 TMDB
python3 app.py import-telegram /path/to/ChatExport --channel lsp115 --workers 8 --no-tmdb

# 2) 导入跑完后再批量补 TMDB 匹配（可反复执行）
python3 app.py match --limit 5000 --workers 8
```

## 标题清洗与重跑匹配

频道里有两种标题形态，解析规则必须都覆盖，否则 TMDB 一定搜不到：

| 正文形态 | 错误标题 | 正确标题 |
| --- | --- | --- |
| 字段式：`名称：飞驰人生2（2024）` + `剧情简介：…` | `名称：飞驰人生2` | `飞驰人生2`（年份 2024） |
| 进度式：`📺 斗战天下 高码率  更新至26` | `斗战天下 高码率  更新至26` | `斗战天下` |
| 集数粘在片名后：`📺 凡人修仙传172` | `凡人修仙传172` | 标题保留，检索时兜底用 `凡人修仙传` |
| 系列成员：`📺 007(系列)` + 文件名 `Live.and.Let.Die.1973` | `007`（还只写系列名） | `007`，并归入「007」系列 |
| 括号被截断：`📺 星球大战（系列` | `星球大战（系列` | `星球大战` |

清洗规则：剥掉 `名称/片名/剧名/资源名称/标题` 前缀、`（系列）/（合集）` 标注、
`高码率/杜比视界/HDR10/1080` 等画质词、`更新至N/更至N/EPn` 等进度尾巴，并截断
未闭合的括号。尾部纯数字只在剧集语境或数字 ≥10 时按集数剥离，`疾速追杀2`、
`美国队长4` 这类真实续集片名不会被误改。

解析规则修好后，存量作品不必重新导入——入库时每条消息的首行都保存在
`resource_metadata_json.context` 里：

```bash
# 预览会改哪些标题（不写库）
python3 app.py retitle

# 落库：只改标题，并把改动的作品重置为 pending，等下一轮 match
python3 app.py retitle --apply
python3 app.py match --limit 5000 --workers 8
```

`retitle` 还会把带系列标记的作品挂到对应系列上（`media_series`），已匹配的作品同样参与
归属（它们本来就该在系列里），但只有未匹配作品的标题会被改写。它跳过人物条目，也**不改写媒体类型和年份**
（它们来自导入时的整段原文，用首行重算会把电影误判成剧集）。`match --workers`
是并发检索：单条作品要发十余个 TMDB 请求，串行时墙钟时间几乎全花在往返上。

### 整包分享

有的消息把**整个系列打成一个 115 分享**（只有分享链接、没有发布文件名）。115 目录列举
已按风控关闭，包里有哪些片子拆不出来，所以这类记录标成整包（`is_bundle`）：不进待匹配
队列、不会被错绑到其中某一部，系列页里显示「整包分享 · N 个来源」。想补全成员，只能靠
`app.py series` 用 TMDB 合集补齐（它按已匹配成员的 `belongs_to_collection` 找同系列的本地作品）。

系列在界面左侧「系列」里查看：一条系列显示成员数和年份跨度，点开是系列内每一部的
TMDB 状态和来源数，再点可跳到该作品的详情。

```bash
curl -s localhost:8088/api/series | head -c 200
python3 app.py match --series --workers 8   # 只补系列成员的 TMDB 匹配
python3 app.py series --apply               # 用 TMDB 合集补齐系列成员
```


## 参数

| 参数 | 说明 |
| --- | --- |
| `path` | 导出目录（或其中的某个 `messages*.html`）；按 `messages.html`、`messages2.html` … 的分页顺序解析 |
| `--channel` | 频道用户名，如 `lsp115`；不传时用导出页头的频道名去既有入库记录里反查 |
| `--channel-id` | 频道数字 ID；默认从既有入库记录复用，保证和 webhook 事件共用同一个事件 ID |
| `--channel-name` | 覆盖导出页头里的频道名 |
| `--limit` | 本次最多处理 N 条；已入库的消息不计入，因此反复带 `--limit N` 可以分批往前推 |
| `--workers` | 并发处理线程数，默认 4；导入用有界线程池驱动同步模式的 `receive`，不会每条消息开一个线程 |
| `--delay` | 每提交一条消息后的额外间隔秒数 |
| `--dry-run` | 只解析统计：消息数、无正文数、已入库数、含直链来源的消息数、需抓取资源页的消息数；不写库、不联网 |
| `--no-tmdb` | 导入时不跑 TMDB 自动匹配，作品留在 `pending` 待匹配状态，事后用 `app.py match` 批量补 |

## 行为

- 事件 ID 为 `telegram:<频道ID>:<消息ID>:v1`，与 webhook 送来的同一条消息一致；
  另外按 (service, 频道用户名, 消息 ID) 预先跳过已入库消息，重复执行安全。
  状态还是 `queued` 的记录（上次导入被打断留下的半截记录）不算已入库，会重新送入
  链路补完，所以 Ctrl-C 中断后直接重跑即可。
- 每条消息走完整入库链路：`👤` 人物上下文、`telegra.ph` 资源页展开、115/123/光鸭
  只读校验、`ingestion_links` 状态、频道头像；TMDB 自动匹配默认开启，可用
  `--no-tmdb` 延后。
- 单条消息失败只记 `error` 并继续，结束时打印失败样例；进度每 50 条输出一次
  状态分布和预计剩余时间。

## 导出格式带来的覆盖率限制

Telegram 桌面版导出只有文字，图片、视频和投票都是 `Not included` 占位：

- 链接的可见文字经常是「点击查看」，导入时统一按 `href` 还原成真实 URL；
- 很多消息把资源页做成机器人按钮，正文里只有占位文字。导入会把按钮里
  **入库用得上**的链接（资源页和 115/123/光鸭/ED2K 直链）补到正文末尾，
  广告和推广链接不补；
- 纯图片消息在导出里没有正文，会被统计成「无正文」并跳过；
- 既没有直链也没有资源页的消息（只有广告、磁力链或纯文字）会作为
  `ignored` 记录保留，不产生来源。

以 115 网盘资源分享频道（lsp115）2026-10-21 的全量导出为例：17,524 条消息里
17,428 条有正文，7,056 条带直链来源，8,345 条只带资源页链接，2,027 条没有任何
受支持的来源。

## 网络代价与分批

导入是**在线**的：每条消息会抓取它引用的资源页，并对每条 115/123/光鸭 分享做一次
只读校验。115 的本地请求闸门（`ShareRequestGate`）全局强制 5 秒 1 次，触发访问限制
后会暂停并要求人工确认恢复，所以：

- 5 秒间隔从「本次请求发起」开始计时（请求返回耗时不再额外串进间隔），闸门里的
  等待和请求仍然被文件锁串行，实际节奏就是每 5 秒一次；`interval` 有 5 秒下限，
  不能靠调小它提速；
- **115 接口自身的响应时间才是主要瓶颈**：实测单次探测 5～35 秒（同一网络下连续
  两次分别为 5.01s 和 35.13s）。因此实际吞吐约 6～12 次探测/分钟，再增加并发也
  不会更快，只会让线程排在闸门后面；
- 先 `--dry-run` 看预估网络量，再用 `--limit 200` 试跑一批，抽查入库记录；
- 之后按批放量，整批放后台跑，随时可以 Ctrl-C 停，再执行一次就自动续跑；
- 115 闸门的 5 秒是风控保护线，`ShareRequestGate` 里写死了 `max(5.0, interval)`，
  不要用改间隔、多进程并跑等方式绕过；
- 大批量导入建议加 `--no-tmdb`：TMDB 搜索不是瓶颈，但每条消息都搜一次会拖慢节奏，
  还容易触发 TMDB 的连接重置，延后用 `app.py match` 批量补反而更快、更稳；
- 闸门一旦进入暂停状态就停下人工处理，不要连续重试绕过限制；
- 大批量校验结束后仍建议执行 `python3 app.py check-shares --resume` 做低频复核。
